# TypeScript web server and browser operator primitives

## Executive answer

**Sub-question A — TS web-server framework.** Fastify is the best v0 fit for an HTTP-terminating TypeScript control-surface process because its official ecosystem has server-side sessions, cookie support, CSRF-token utilities, WebSocket support, lifecycle hooks, plugin encapsulation, and a first-party Connect-ES Fastify server plugin path; the fetched npm metadata shows current packages in scope are Fastify `5.10.0`, `@fastify/session` `11.1.1`, `@fastify/cookie` `11.0.2`, `@fastify/csrf-protection` `8.0.0`, and `@fastify/websocket` `11.2.0` [npm-registry-web-stack]{2} [npm-registry-web-stack]{3} [npm-registry-web-stack]{4} [npm-registry-web-stack]{5} [npm-registry-web-stack]{6}. Fastify's session/CSRF stack still needs explicit hardening: configure `cookieName: '__Host-patchbay_session'`, no `Domain`, `Path=/`, `Secure`, `HttpOnly`, `SameSite=Strict`, a production store, `saveUninitialized: false`, a session-stored CSRF secret, a custom CSRF header extractor, and separate Origin/Fetch-Metadata checks rather than relying on plugin defaults alone [fastify-session]{6} [fastify-session]{8} [fastify-session]{9} [fastify-csrf]{2} [fastify-csrf]{4} [fastify-csrf]{8} [owasp-session-management]{6} [owasp-session-management]{7} [owasp-csrf]{4} [owasp-csrf]{5}.

**Sub-question B — browser operator-domain primitives.** Use Connect-Web for unary browser RPCs and server-streaming browser RPCs, use TanStack Query for server-state cache/snapshot fetches only, and use XState or a generated reducer for explicit protocol-derived presentation machines. XState is a good fit for finite/parallel local presentation and reconnect workflow logic because it models deterministic transitions, statecharts, actors, subscriptions, and persistence; it should not become the source of truth for Patchbay's protocol registries unless generated from them [xstate-docs]{2} [xstate-docs]{3} [xstate-docs]{4} [xstate-docs]{6} [xstate-docs]{9} [xstate-docs]{10}. TanStack Query fits snapshot/revalidation/cache mechanics because it has explicit stale/cache/refetch/reconnect/network-mode behavior, but its `stale` and `paused` concepts are library cache states, not authoritative Patchbay session connectivity or command states [tanstack-query-docs]{1} [tanstack-query-docs]{3} [tanstack-query-docs]{7} [tanstack-query-docs]{8}. Connect-Web fits browser calls to a TS web server and supports server streaming through async iterables, but browser Connect clients are limited to server streaming rather than client/bidirectional streaming because browsers lack broadly supported streaming request bodies [connect-es-web]{1} [connect-es-web]{2} [connect-es-web]{5}.

## Sub-question A — TS web-server framework

### Required shape from the grounding docs

The web process must terminate HTTP/HTTPS, own operator sessions, cookies, and CSRF, and act as a control surface rather than the durable authority. That means framework ergonomics are secondary to security wiring: the framework must make it boring to add request hooks, server-side session storage, cookie attributes, CSRF-token verification, Origin/Fetch-Metadata checks, Connect/Protobuf transport, and stream endpoints.

### Current package snapshot

The npm registry metadata fetched for this facet reports Hono `4.12.28`, Fastify `5.10.0`, Elysia `1.4.29`, XState `5.32.4`, TanStack React Query `5.101.2`, and Connect-ES web/node packages `2.1.2` [npm-registry-web-stack]{1} [npm-registry-web-stack]{2} [npm-registry-web-stack]{7} [npm-registry-web-stack]{8} [npm-registry-web-stack]{9} [npm-registry-web-stack]{10}. These version claims should be refreshed before implementation begins, but they are current for this research pass.

### Fastify

Fastify has the most direct fit for v0 because its official docs make plugins and request lifecycle hooks first-class: plugins can add routes/decorators/functionality via `register`, `register` creates encapsulated scopes by default, and request/reply hooks include `onRequest`, `preValidation`, and `preHandler` with scope support [fastify-docs]{1} [fastify-docs]{2} [fastify-docs]{4} [fastify-docs]{5} [fastify-docs]{6}. That matches a security boundary where cookie parsing, session loading, CSRF validation, Origin/Fetch-Metadata validation, audit correlation, and route protection should be ordered and scoped.

For cookies, `@fastify/cookie` parses cookies through `onRequest`, supports signed cookies and key rotation, defaults `Domain` to unset, and exposes `httpOnly`, `sameSite`, and `secure` controls, but its README says `HttpOnly` and `Secure` are not set by default at the raw cookie-plugin layer [fastify-cookie]{2} [fastify-cookie]{4} [fastify-cookie]{6} [fastify-cookie]{7} [fastify-cookie]{8} [fastify-cookie]{9}. For sessions, `@fastify/session` requires `@fastify/cookie`, stores session data server-side using the configured session store, defaults the session cookie name to `sessionId`, defaults `path` to `/`, `httpOnly` to true, `secure` to true, and warns that the default in-memory store should not be used in production [fastify-session]{1} [fastify-session]{3} [fastify-session]{5} [fastify-session]{6} [fastify-session]{8}. Therefore Fastify can meet the hardened-cookie and server-side-session requirement, but only with explicit configuration: change the cookie name to `__Host-patchbay_session`, set `SameSite=Strict`, avoid `Domain`, keep `Secure`/`HttpOnly`, trust the reverse proxy only when intentionally deployed behind one, and supply a durable production store.

For CSRF, `@fastify/csrf-protection` is usable but not sufficient by default. It explicitly says CSRF security remains the developer's responsibility and third-party modules should not be fully trusted; with `@fastify/session`, it stores the CSRF secret in the session; `fastify.csrfProtection` can protect routes/hooks; and the token extractor can be customized, which the README recommends for performance and security [fastify-csrf]{1} [fastify-csrf]{2} [fastify-csrf]{4} [fastify-csrf]{8} [fastify-csrf]{9}. This lines up with OWASP's stateful synchronizer-token guidance: generate server-side tokens per session or per request, store/compare them against session state, reject missing/mismatched tokens, use custom AJAX headers, and avoid GET for state changes [owasp-csrf]{2} [owasp-csrf]{3} [owasp-csrf]{4} [owasp-csrf]{5} [owasp-csrf]{7} [owasp-csrf]{9}. Fastify still needs an additional hook for Origin and/or Fetch Metadata because the CSRF package attested here is a token utility rather than a complete Origin/Fetch-Metadata policy [fastify-csrf]{2} [owasp-csrf]{9}.

For browser streaming, `@fastify/websocket` is first-party and integrates with the Fastify router and pre-upgrade hooks; it says `onRequest`, `preParsing`, `preValidation`, and `preHandler` hooks run before WebSocket establishment and can be used for authentication, but post-upgrade message handling is outside Fastify's HTTP response lifecycle [fastify-websocket]{1} [fastify-websocket]{2} [fastify-websocket]{5} [fastify-websocket]{6}. This is acceptable for a WebSocket endpoint if the initial upgrade is session/CSRF/Origin checked and message-level authorization remains explicit. The fetched first-party Fastify material did not provide a Fastify-owned SSE helper, so SSE on Fastify should be treated as custom response streaming or an additional package decision rather than a documented first-party capability {confidence: fetched-docs-only}.

Fastify also has the cleanest Connect-ES integration. Connect's Node server-plugin docs explicitly recommend Fastify when serving other things along with Connect RPCs, show `@connectrpc/connect-fastify`, and say Fastify over HTTP/2 can serve Connect, gRPC, and gRPC-Web with all RPC types; over HTTP/1.1, gRPC and bidirectional streaming are not supported [connect-es-node]{6} [connect-es-node]{7} [connect-es-node]{8}. For outbound TS-web-server-to-Rust-core calls, `@connectrpc/connect-node` provides Node client transports using Node `http`, `https`, and `http2` modules [connect-es-node]{1} [connect-es-node]{2} [connect-es-node]{4}. If the browser talks Connect to the web server and the web server talks Connect/gRPC to the Rust core, Fastify is the only candidate in this comparison with a fetched first-party Connect server-plugin path [connect-es-node]{9}.

### Hono

Hono is attractive if the v0 implementation wants Web-standard request/response portability and compact middleware: Hono describes handlers as returning `Response` and middleware as an onion around request/response handling [hono-docs]{1}. Its cookie helper supports regular/signed cookies, cookie options including `httpOnly`, `secure`, `sameSite`, and `prefix`, and explicit `__Host-` validation failures when `secure`, `path=/`, or no-`domain` constraints are violated [hono-docs]{2} [hono-docs]{3} [hono-docs]{4}. Hono also has a documented CSRF middleware that validates `Origin` and `Sec-Fetch-Site`, a WebSocket helper across Cloudflare/Deno/Bun/Node adapters, and an SSE streaming helper [hono-docs]{5} [hono-docs]{7} [hono-docs]{9}.

The blocker is that the fetched Hono docs do not provide a framework-owned server-side session plugin or synchronizer-token CSRF solution. Hono's CSRF page warns that old browsers without Origin headers or proxies that remove them may require other CSRF token methods, and OWASP says stateful software should use synchronizer tokens stored in session state rather than relying only on header/origin mitigations [hono-docs]{6} [owasp-csrf]{3} [owasp-csrf]{4}. Hono could still be made safe with custom session storage and token middleware, but that moves v0 security burden into application-owned wiring. The fetched Connect-ES Node docs also did not list a Hono server plugin among first-party Node integrations [connect-es-node]{9}. Hono is a plausible second choice if framework portability is prioritized over ready-made security/connect plugins, but it is not the lowest-risk v0 default.

### Elysia

Elysia's strengths are Bun-oriented TypeScript ergonomics, reactive cookies, built-in cookie signing/rotation, and a concise WebSocket API. Its docs say it is optimized for Bun but not limited to Bun through WinterTC-compatible deployment targets, and the cookie docs describe mutable cookie signals, automatic header synchronization, cookie signatures, and secret rotation [elysia-docs]{1} [elysia-docs]{2} [elysia-docs]{3} [elysia-docs]{5} [elysia-docs]{6}. Elysia exposes `httpOnly`, `sameSite`, and `secure` cookie controls, but its docs say `httpOnly` defaults false and `secure` is not set by default [elysia-docs]{7}. Elysia's WebSocket support is documented through `Elysia.ws()` with schema validation over message, query, params, header, cookie, and response [elysia-docs]{8} [elysia-docs]{9}.

For this v0 question, Elysia is weaker than Fastify because the fetched docs surfaced no official server-side session plugin or CSRF plugin, and the JWT plugin example demonstrates JWT-in-cookie usage rather than a server-side opaque-session model [elysia-docs]{10} [elysia-docs]{11}. Elysia may be productive for a Bun-native service, but Patchbay's browser session posture should not be driven toward JWT/cookie bearer semantics when OWASP recommends meaningless identifiers with application/session meaning stored server-side [owasp-session-management]{2}. It would require custom session and CSRF middleware plus a custom Connect integration path, so it is not the recommended v0 server framework.

### Oak / Deno-native

Oak is a capable Deno-origin middleware framework with cookies, signing keys, SSE, and WebSocket upgrade APIs. Its README says oak targets Deno native HTTP, Deno Deploy, Node.js, Cloudflare Workers, and Bun, uses an application/context middleware stack, supports signing/verifying cookies through application keys, exposes `sendEvents()` for server-sent events, and exposes `upgrade()` for WebSocket connections [oak-docs]{1} [oak-docs]{5} [oak-docs]{6} [oak-docs]{7} [oak-docs]{8} [oak-docs]{9} [oak-docs]{10}.

Oak is not the v0 default because its own README notes that Node.js usage through JSR does not currently support Send, WebSocket upgrades, or TLS/HTTPS serving, and Bun/Cloudflare usage does not currently support Send or WebSocket upgrades [oak-docs]{3} [oak-docs]{4}. The fetched README also did not describe a built-in server-side session plugin or CSRF token middleware [oak-docs]{11}. Oak remains a good Deno-native reserved seam, but it adds runtime and security-wiring uncertainty relative to Fastify.

### Session / CSRF / cookie library conclusion

The browser-session cookie should use `__Host-`, `Path=/`, no `Domain`, `Secure`, `HttpOnly`, and `SameSite=Strict` because MDN and OWASP both describe `__Host-` constraints, OWASP recommends `__Host-` for session IDs, OWASP prefers `SameSite=Strict` or `Lax`, and MDN states that `Secure` is HTTPS-only except localhost [mdn-set-cookie]{3} [mdn-set-cookie]{4} [mdn-set-cookie]{5} [owasp-session-management]{4} [owasp-session-management]{5} [owasp-session-management]{6} [owasp-session-management]{7}. The session identifier should be high-entropy, CSPRNG-generated, meaningless to the client, and backed by server-side session state because OWASP requires at least 64 bits of entropy, recommends CSPRNG generation, and says application meaning belongs server-side [owasp-session-management]{1} [owasp-session-management]{2} [owasp-session-management]{3}. The Fastify stack can satisfy these requirements with explicit configuration and a production store; Hono/Elysia/Oak require more custom wiring for the server-side session + CSRF-token layer.

## Sub-question B — browser operator-domain primitives

### XState vs hand-rolled state machines

XState is reusable for local operator-domain presentation and reconnect workflow machines because the docs directly support deterministic transitions, statecharts with hierarchy/parallelism, actors with event mailboxes, emitted snapshots, subscriptions, persisted snapshots, and event-sourced restoration [xstate-docs]{3} [xstate-docs]{4} [xstate-docs]{6} [xstate-docs]{7} [xstate-docs]{8} [xstate-docs]{9} [xstate-docs]{10} [xstate-docs]{11}. This maps well to UI-local axes such as connectivity × activity and reconnect phases, especially when stale/offline/unknown presentation must avoid impossible combinations.

The caveat is source-of-truth ownership. XState docs present machine definitions as application logic, while Patchbay's protocol state registries are supposed to be canonical elsewhere; therefore the browser should either generate XState machines from the protocol registry or use thin hand-rolled reducers derived from generated enum/types. If XState machine definitions are hand-authored separately, they become a competing state registry {inferred: architectural-risk-from-source-and-project-constraints}. XState's persistence caveats also matter: persisted states can become incompatible if actor logic changes, actions are not re-executed on restoration, and persisted state must be JSON-serializable [xstate-docs]{12}. For reconnect correctness, authoritative snapshots and cursor replay should come from Patchbay's server/core protocol, not from restoring a local XState snapshot alone.

Recommendation: use XState for non-authoritative browser workflow orchestration only if machine generation or strict registry conformance tests are planned; otherwise start with generated discriminated-union reducers and add XState later for complex nested/parallel UI flows.

### TanStack Query cache/reconnect patterns

TanStack Query is a good fit for server-state queries such as session lists, detail snapshots, grant summaries, and stale snapshot refetches because it explicitly models stale cache, cache retention, reconnect refetch, offline pause, and focus-driven revalidation [tanstack-query-docs]{1} [tanstack-query-docs]{2} [tanstack-query-docs]{3} [tanstack-query-docs]{5} [tanstack-query-docs]{6}. It also exposes useful nuance: `pending` can coexist with `fetchStatus: 'paused'`, retries can pause while offline and continue after reconnection, and `offlineFirst` can run once from local/HTTP cache before pausing retries [tanstack-query-docs]{7} [tanstack-query-docs]{8} [tanstack-query-docs]{9} [tanstack-query-docs]{10}. Those mechanics can help render honest loading/stale/offline states without inventing protocol states.

The boundary is that TanStack Query's `stale`, `paused`, and cache garbage collection are library state, not Patchbay protocol state. It should not decide whether a runtime session is live/stale/offline/unknown, whether a command is retry-safe, or whether a snapshot is authoritative {inferred: boundary-from-source-and-project-constraints}. Configure `staleTime`, `refetchOnReconnect`, and focus behavior deliberately; the defaults refetch stale queries on focus and network reconnect, which is useful for freshness but can mislead if UI labels treat a refetch as authoritative liveness [tanstack-query-docs]{3} [tanstack-query-docs]{4} [tanstack-query-docs]{11}.

Recommendation: use TanStack Query for cache and snapshot fetch plumbing, but keep subscription streams, cursor reconciliation, and protocol-derived state labels outside Query's cache-state vocabulary.

### Connect-Web browser client

Connect-Web is a good fit for browser-to-TS-web-server typed calls. The docs say Connect can call remote procedures from the browser with a type-safe client, `createClient` gives promise-based clients, server-streaming methods return async iterables, and `@connectrpc/connect-web` provides fetch-based `createConnectTransport()` [connect-es-web]{1} [connect-es-web]{4} [connect-es-web]{5} [connect-es-web]{9}. It also supports gRPC-web transport when the backend supports that protocol, and custom fetch can include credentials such as cookies [connect-es-web]{8} [connect-es-web]{11} [connect-es-web]{12}.

Streaming support is specifically server-streaming only from the browser side: Connect says the protocol supports all streaming RPCs, but browsers do not broadly support client streaming request bodies, so browser clients can use only server streaming [connect-es-web]{2}. That is sufficient for server-to-browser event/reply streams if the TS web server exposes a server-streaming RPC; it is not sufficient for browser-driven bidirectional streaming. Timeouts are available and relevant for fragile network streams because Connect sends timeout values in a header understood by Connect, gRPC, and gRPC-web servers [connect-es-web]{13}.

### WebSocket / SSE support from web server to browser

For typed, protocol-derived event streams, prefer Connect server-streaming first because it keeps browser calls in the same generated Protobuf/Connect client stack and supports async iterable consumption [connect-es-web]{5}. Use SSE when a simple one-way event feed is easier to operate or debug; Hono documents `streamSSE()` and Oak documents `sendEvents()` [hono-docs]{9} [oak-docs]{9}. Fastify does not have a fetched first-party SSE helper in this pass, so Fastify SSE should be treated as custom streaming or a separately researched plugin {confidence: fetched-docs-only}. Use WebSocket when the browser needs bidirectional low-latency messaging; Fastify's WebSocket plugin is first-party and hook-integrated before upgrade, Hono has adapter-dependent WebSocket helpers with middleware/header caveats, Elysia has a Bun/uWebSocket-backed `.ws()` API, and Oak exposes `upgrade()` but lacks WebSocket upgrades on Node/Bun/Cloudflare per its README [fastify-websocket]{1} [fastify-websocket]{5} [hono-docs]{7} [hono-docs]{8} [elysia-docs]{8} [oak-docs]{3} [oak-docs]{4} [oak-docs]{10}.

Security implication: HTTP session/cookie/CSRF checks cover ordinary state-changing HTTP/Connect mutations, but WebSocket message streams need an authenticated upgrade plus message-level authority checks because Fastify documents that message handling after upgrade is outside HTTP response hooks [fastify-websocket]{5} [fastify-websocket]{6}. SSE and Connect server-streaming are one-way from server to browser; they still need authenticated subscription authorization and cursor/snapshot reconciliation, but they avoid browser-to-server message mutation inside a long-lived socket.

## Disconfirming analysis

Fastify's strongest disconfirming evidence is not that it cannot satisfy the requirements, but that its security plugins are not secure-by-default enough for this use case. `@fastify/cookie` does not default `HttpOnly` or `Secure`, `@fastify/session` defaults the cookie name to `sessionId`, the default session store is explicitly not production-safe, and `@fastify/csrf-protection` warns that CSRF security remains developer responsibility [fastify-cookie]{7} [fastify-cookie]{9} [fastify-session]{5} [fastify-session]{8} [fastify-csrf]{2}. This does not overturn the recommendation because the same or greater custom-security burden appears for Hono, Elysia, and Oak in the fetched sources, while Fastify at least supplies the session-store and CSRF-token primitives [fastify-session]{3} [fastify-csrf]{4}.

Hono's disconfirming evidence is strong on portability and SSE: it has Web-standard middleware, robust cookie-prefix validation, Origin/Fetch-Metadata CSRF middleware, WebSocket helpers, and `streamSSE()` [hono-docs]{1} [hono-docs]{4} [hono-docs]{5} [hono-docs]{7} [hono-docs]{9}. That would make Hono preferable if v0 prioritized runtime portability and SSE simplicity over ready-made server-side sessions and official Connect server plugins. It does not overtake Fastify for this facet because OWASP's stateful CSRF pattern requires session-tied tokens, and the fetched Hono docs themselves say to use other token methods when header-based CSRF does not fit [hono-docs]{6} [owasp-csrf]{3} [owasp-csrf]{4}.

Elysia's disconfirming evidence is strong on TypeScript ergonomics and WebSocket/schema validation, and its docs claim non-Bun deployment targets despite Bun optimization [elysia-docs]{1} [elysia-docs]{2} [elysia-docs]{8} [elysia-docs]{9}. It remains weaker for v0 because the fetched docs did not surface server-side sessions or CSRF tokens, and its documented JWT plugin points toward a bearer-token style that is not the target browser-session model [elysia-docs]{10} [owasp-session-management]{2}.

Oak's disconfirming evidence is that it has Deno-native maturity and built-in SSE/WebSocket/cookie primitives [oak-docs]{1} [oak-docs]{8} [oak-docs]{9} [oak-docs]{10}. It remains weaker for a TS web-control process because the README states WebSocket/TLS limitations outside Deno and did not provide server-side sessions or CSRF-token middleware [oak-docs]{3} [oak-docs]{4} [oak-docs]{11}.

For browser state, the disconfirming argument against XState is that a registry-driven protocol may be safer with generated reducers than with a separate runtime statechart library. XState's own persistence caveats strengthen that concern: incompatible logic changes and serialization limits matter for long-lived operator sessions [xstate-docs]{12}. The counterweight is that XState's deterministic/parallel/actor/snapshot model is exactly the kind of machinery needed for complex UI workflows [xstate-docs]{3} [xstate-docs]{6} [xstate-docs]{7} [xstate-docs]{9}. The disciplined compromise is generated/conformance-tested machines or hand-rolled generated reducers.

For browser data, the disconfirming argument against TanStack Query is that it can blur `stale` cache semantics with Patchbay's protocol stale/offline/unknown semantics. The docs explicitly show library-level stale/refetch/reconnect behavior and a `pending` query with `fetchStatus: 'paused'`, which is useful but not the same as authoritative control-plane state [tanstack-query-docs]{1} [tanstack-query-docs]{3} [tanstack-query-docs]{8}. Therefore it is suitable for cache plumbing, not protocol authority.

## Contradictions

No hard source contradiction surfaced. The main tensions are:

## Revisit if

- The Rust core facet decides the web↔core seam is not Connect/gRPC/Protobuf.
- The v0 web server must run on Deno, Bun, or edge workers rather than Node.js.
- Fastify's session/CSRF plugins change defaults or lose maintenance compatibility with Fastify v5.
- Hono gains an official server-side session + synchronizer-token CSRF plugin and a first-party Connect server integration.
- Elysia gains first-party server-side session/CSRF docs and a Connect plugin.
- Browser requirements need bidirectional streaming over a single channel rather than unary mutations plus server stream/SSE.
- Offline-first native/Expo scope enters v0 and changes browser-only assumptions.

# Attestation: OWASP Session Management Cheat Sheet

## Summary

The OWASP Session Management Cheat Sheet gives implementation guidance for web session identifiers and session cookies. It requires high-entropy, meaningless session IDs, recommends server-side storage of session state, calls for `Secure`, `HttpOnly`, and `SameSite` cookie protections, recommends `__Host-` cookie prefixes for session IDs, and requires session ID renewal after privilege-level changes.

## Key passages

1. From "Session ID Entropy":

> Session identifiers must have at least 64 bits of entropy to prevent brute-force session guessing attacks. ... A strong CSPRNG (Cryptographically Secure Pseudorandom Number Generator) must be used to generate session IDs.

2. From "Session ID Content (or Value)":

> The session ID content (or value) must be meaningless to prevent information disclosure attacks ... The session ID must simply be an identifier on the client side, and its value must never include sensitive information or Personally Identifiable Information (PII). ... The meaning and business or application logic associated with the session ID must be stored on the server side.

3. From "HttpOnly Attribute":

> The `HttpOnly` cookie attribute instructs web browsers not to allow scripts ... to access the cookies via the DOM `document.cookie` object. This session ID protection is mandatory to prevent session ID stealing through XSS attacks. ... The `HttpOnly` cookie only protects the confidentiality of the cookie.

4. From "SameSite Attribute":

> The `SameSite` attribute prevents the browser from sending the cookie on cross-site requests, mitigating cross-origin leakage and providing CSRF defense. Session cookies must explicitly set `SameSite=Strict` (preferred) or `SameSite=Lax`. Never use `SameSite=None` without `Secure`, and do not rely on the browser-default value.

5. From "Cookie Name Prefixes":

> `__Host-` — the cookie must be set with `Secure`, must not have a `Domain` attribute, and must use `Path=/`. Prevents subdomain forgery and HTTPS downgrade attacks. Recommended for session IDs.

6. From "Renew the Session ID After Any Privilege Level Change":

> The session ID must be renewed or regenerated by the web application after any privilege level change within the associated user session. ... Common scenarios to consider include; password changes, permission changes, or switching from a regular user role to an administrator role.

# Design Checkpoints

Agile-workflow design skills (`feature-design`, `epic-design`, `refactor-design`, `perf-design`, `e2e-test-design`) instruct the agent to use a "structured question tool" at Phase 4.5 ambiguity checkpoints. This harness does not always provide one, and structured-question UIs do not render on remote_pi peers. The checkpoint is still mandatory; only the rendering changes.

- **When a skill says "use structured question tool" and no such tool is available: ask the user in plain text.** Do NOT resolve with judgment, do NOT log a `## Design decisions` entry, and do NOT advance the stage until the user answers. Surface 2–5 concrete questions grounded in the actual feature — the shape the tool would have presented.
- **Tool absence does not invoke autopilot judgment-mode.** Judgment-mode (resolve with judgment + log rationale) is gated on an *active autopilot queue goal* driving the skill (`principles/SKILL.md` Part III), not on the tool being missing. A direct user invocation is interactive regardless of tool availability — the user is the alignment signal and must not be bypassed because the tool failed to render.
- **Plain-text asks are the portable default.** Prefer them even when a structured-question tool exists, unless the tool adds real value (many options, multi-select). Plain text works identically on local pi and remote_pi; structured UIs do not.
- **The work-nature test runs before asking.** If a docs-only surface is genuinely zero (authoring a checklist/inventory of already-settled material), record "zero questions" and collapse to the lightweight writing pass — do not manufacture questions to satisfy the form. But when in doubt, surface the question: the cost of asking is low; the cost of a silent semantic commitment is high.

# Story: Conformance vectors for the elicitation response contract

Checkpoint for `feature-v0-elicitation-response-contract` Unit 4. Pins the
three committed response shapes and four rejection classes as executable
conformance vectors — the earned-not-asserted check (the lesson from the
prior session's component-layer arc).

## Deliverable

Seven conformance vectors in `contracts/vectors/`, using the existing
envelope (`vector_id`, `property_id`, `promotion_status`,
`proto_fields_constrained`, `description`, `input`, `expected_outcome`,
`invariant_check`):

**Acceptance vectors** (property_id: `ElicitationInvalidResponseRejected` —
they exercise the valid side: a valid response is accepted, not rejected):
1. `elicitation-response-question-select-one.json` — valid `selected_option_id`
   matching a contract option.
2. `elicitation-response-question-free-text.json` — valid `free_text` when
   `allow_free_text == true`.
3. `elicitation-response-question-answer-and.json` — valid selected option +
   EC2 `clarification`.

**Rejection vectors** (property_id: `boundary-validation` — descriptive
draft; the fine-grained rejection rules are boundary validation, not a named
formal property):
4. `elicitation-response-invalid-mismatched-option.json` — `selected_option_id`
   not in the contract's options.
5. `elicitation-response-invalid-free-text-disallowed.json` — `free_text` when
   `allow_free_text == false`.
6. `elicitation-response-invalid-both-primary-answers.json` — both
   `selected_option_id` and `free_text` set.
7. `elicitation-response-invalid-terminal-elicitation.json` — response against
   an already-terminal elicitation.

## Acceptance evidence

- [ ] All seven vectors exist with correct envelopes and pass `check:vectors`.
- [ ] Each `proto_fields_constrained` references real fields added in Unit 1:
      `patchbay.ResponseContract.question`, `patchbay.QuestionContract.options`,
      `patchbay.QuestionContract.allow_free_text`, `patchbay.ResponseOption.option_id`,
      `patchbay.ElicitationResponsePayload.selected_option_id`,
      `patchbay.ElicitationResponsePayload.free_text`,
      `patchbay.ElicitationResponsePayload.clarification`.
- [ ] `input` carries a full `Elicitation` (opening, with its
      `response_contract.question`) + the response `Operation` with a serialized
      `ElicitationResponsePayload`. `expected_outcome` states `accepted`/
      `rejected` + `failure_code` (`validation_failed` for rejections).
- [ ] The generated conformance-traceability table in `docs/VERIFICATION.md`
      (regenerated by `check:vectors`) lists the new vectors under
      `ElicitationInvalidResponseRejected` and `boundary-validation`.
- [ ] CI's "Protocol conformance vectors" step passes with the new vectors.

## Notes

- The `check-vectors` script validates envelope + property-id registry but
  does **not** execute the core's validation against the vector input (no
  invariant-expectation checker registered for these properties yet — see
  `INVARIANT_EXPECTATION_CHECKS` in `check-vectors.mjs`). The vectors are
  therefore *contract-specifying* (they pin shape + property for review) but
  not yet *executable-against-the-core*. The Rust unit tests in Unit 2 are
  the executable check today. Registering a JS-side checker is the promotion
  path — a clean follow-on, not a v0.1.0 blocker (flagged in the feature's
  Risks so review does not mistake the vectors for an unenforced claim).
- `property_id` choices: acceptance vectors reference the stated-normative
  `ElicitationInvalidResponseRejected` (already in the `check-vectors`
  registry); rejection vectors reference the descriptive `boundary-validation`
  id (draft-only, per the registry) since fine-grained rejection rules are
  boundary validation, not a named formal property.

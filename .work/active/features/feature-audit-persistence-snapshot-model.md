## Alternatives evaluation

- **Persistence backend abstraction (Ports & Adapters).** Landed: v0 uses a single-writer, local-first durable store owned by the coordination core, accessed through a storage port; the first backend may be embedded, but semantics must not depend on the backend (`docs/ARCHITECTURE.md:164`, `docs/ARCHITECTURE.md:167`, `docs/ARCHITECTURE.md:168`; `docs/PROTOCOL.md:463`, `docs/PROTOCOL.md:464`, `docs/PROTOCOL.md:465`). Alternatives: (1) mandate one storage engine up front, optimizing implementation simplicity but leaking DB/file assumptions into core semantics; (2) remote-replicated/HA storage from day one, optimizing availability but overbuilding against the v0 single-authoritative-core commitment (`docs/ARCHITECTURE.md:137`, `docs/ARCHITECTURE.md:171`); (3) adapter-owned persistence, optimizing adapter autonomy but violating core ownership of durable command state. Why landed: it honors Ports & Adapters while keeping v0 small.
- **Event log / inbox / command-state ownership and single ordered log.** Landed: the core owns durable command state, event log, snapshots, and audit records through the storage port; one authoritative core process writes the log (`docs/PROTOCOL.md:459`, `docs/PROTOCOL.md:461`, `docs/PROTOCOL.md:463`). Alternatives: (1) per-session logs, optimizing local replay but complicating terminal races and cross-session ordering; (2) outbox-per-adapter delivery ownership, optimizing integration with adapter queues but weakening the core's durable acceptance boundary; (3) append-only audit only, optimizing traceability but not recovery. Why landed: first-terminal-commit-wins and snapshot reconciliation need one core-owned durable order.
- **`(authority_domain_id, LSN)` key shape.** Landed: event/cursor/revision identity is `(authority_domain_id, LSN)`, with one domain in v0 but a domain demarcator in the durable key (`docs/PROTOCOL.md:84`, `docs/PROTOCOL.md:407`, `docs/PROTOCOL.md:409`). Alternatives: (1) bare LSN, simplest for single-domain v0 but a later migration hazard; (2) HLC/logical-clock abstraction, better for federation but premature. This was already classified by `feature-extension-seams-non-foreclosure` as forward-compatibility hygiene and a federation seam (`.work/active/features/feature-extension-seams-non-foreclosure.md:30`, `.work/active/features/feature-extension-seams-non-foreclosure.md:62`), so this audit does not re-decide it.
- **Core restart/crash recovery.** Landed: accepted Operations are durably recorded before delivery; restart replays the log or latest snapshot plus tail, and accepted Operations are restored rather than disappearing silently (`docs/ARCHITECTURE.md:170`; `docs/PROTOCOL.md:466`, `docs/PROTOCOL.md:467`, `docs/PROTOCOL.md:468`). Alternatives: (1) best-effort in-memory delivery, optimizing simplicity but losing accepted commands on crash; (2) snapshot-only recovery, optimizing replay speed but making snapshots an ordering authority; (3) exactly-once adapter execution, optimizing operator confidence but impossible at the core boundary without adapter-specific guarantees. Why landed: core can guarantee boundary durability and replay; adapter execution idempotency remains a declared capability, not a hidden promise.
- **Snapshot revision/cursor model and older-snapshot rejection.** Landed: snapshots/revisions/cursors are LSN-based; reconnect submits a cursor; older, cross-domain, or wrong-generation snapshots are rejected as authority sources (`docs/PROTOCOL.md:411`, `docs/PROTOCOL.md:415`, `docs/PROTOCOL.md:416`, `docs/UX.md:33`). Alternatives: (1) wall-clock freshness, optimizing UX intuition but failing under clock skew and missed streams; (2) snapshot-version-only freshness, optimizing snapshot storage but disconnecting from event ordering; (3) UI cache authority, optimizing perceived continuity but violating snapshot correctness. Why landed: LSN-derived revisions compose with the event log and keep UI state non-authoritative.
- **Adapter snapshot capability tiers.** Landed: authoritative / partial / none, with degraded behavior rules (`docs/PROTOCOL.md:551`, `docs/PROTOCOL.md:553`, `docs/PROTOCOL.md:561`, `docs/PROTOCOL.md:562`). Alternatives: (1) boolean snapshot support, simpler manifest but forces partial adapters to lie or over-degrade; (2) tier every capability, uniform but speculative; (3) no capability declaration, simpler protocol but poor UX and unsafe reconnect claims. This was re-opened and ratified by `feature-session-identity-adapter-contract`, which explicitly carried over the prose-lane gap (`.work/active/features/feature-session-identity-adapter-contract.md:22`, `.work/active/features/feature-session-identity-adapter-contract.md:49`, `.work/active/features/feature-session-identity-adapter-contract.md:64`, `.work/active/features/feature-session-identity-adapter-contract.md:65`).
- **Event-stream vs snapshot atomicity.** Landed: event streams are optimizations, snapshots read a consistent log prefix, terminal transitions commit before appearing in snapshots/control surfaces, and a backend that cannot provide the atomicity fails rather than exposing inconsistent views (`docs/PROTOCOL.md:422`, `docs/PROTOCOL.md:424`, `docs/PROTOCOL.md:431`; `docs/UX.md:33`). Alternatives: (1) stream-authoritative UI, optimizing latency but losing reconnect correctness; (2) snapshot-as-second-ordering-source, optimizing bulk reads but breaking first-terminal-commit-wins; (3) eventual snapshot writes, optimizing throughput but allowing stale live rendering. Why landed: one ordering authority is the only coherent recovery model.

## Faulty-assumption hunt

- **Ports & Adapters boundary: holds.** The storage decision does not leak a concrete DB/filesystem API into domain semantics. ARCHITECTURE allows an embedded first backend but immediately states domain semantics must not depend on backend choice and that all reads/writes cross a storage port (`docs/ARCHITECTURE.md:167`, `docs/ARCHITECTURE.md:168`); PROTOCOL repeats local-first plus port-isolated ownership (`docs/PROTOCOL.md:464`, `docs/PROTOCOL.md:465`). This is a real port boundary, not merely a doc label.
- **Core-owned log/order/inbox state: holds.** Current first principles still require a core-owned durable order because `CommandState` is durable core state and LSN determines first-terminal-commit and reconciliation (`docs/PROTOCOL.md:407`; `docs/VERIFICATION.md:29`, `docs/VERIFICATION.md:455`). Per-session or adapter-owned logs would force later reconciliation rules to invent an ordering authority.
- **`(authority_domain_id, LSN)` seam: holds.** The landed shape survives because it is low-cost in v0 and avoids retrofitting domain identity into historical event keys. It is already classified as a committed key shape / federation seam (`docs/PROTOCOL.md:599`, `docs/PROTOCOL.md:612`; `.work/active/features/feature-extension-seams-non-foreclosure.md:97`).
- **Crash recovery guarantee: holds with caveat.** The product requirement is coherent, but the checked-status must be stated precisely. `command_lifecycle.qnt` checks `CommandDurability` for accepted records existing in the command map (`specs/seed/command_lifecycle.qnt:123`, `specs/seed/command_lifecycle.qnt:129`, `specs/seed/command_lifecycle.qnt:133`, `specs/seed/command_lifecycle.qnt:135`), and VERIFICATION classifies those lifecycle properties as checked-model (`docs/VERIFICATION.md:25`, `docs/VERIFICATION.md:29`, `docs/VERIFICATION.md:455`). Crash-specific `CrashNoAcceptedLost` and `IdempotentLogReplay` are not checked today: `snapshot_recovery.qnt` says the snapshot/recovery model is deferred (`specs/seed/snapshot_recovery.qnt:6`), marks those properties draft with TBD invocations (`specs/seed/snapshot_recovery.qnt:419`, `specs/seed/snapshot_recovery.qnt:425`, `specs/seed/snapshot_recovery.qnt:438`, `specs/seed/snapshot_recovery.qnt:444`), and VERIFICATION classifies them stated-normative (`docs/VERIFICATION.md:37`, `docs/VERIFICATION.md:41`, `docs/VERIFICATION.md:385`, `docs/VERIFICATION.md:400`). So: accepted-command durability is checked-model; crash recovery is a stated product obligation, not a checked guarantee yet.
- **Snapshot revision/cursor / older-snapshot rejection: holds with caveat.** The protocol rules are sound, but their model status is draft/stated: `snapshot_recovery.qnt` reserves `SnapshotStaleRejected`, `SnapshotCrossDomainRejected`, and `SnapshotConsistentPrefix` with draft/TBD promotion metadata (`specs/seed/snapshot_recovery.qnt:342`, `specs/seed/snapshot_recovery.qnt:348`, `specs/seed/snapshot_recovery.qnt:366`, `specs/seed/snapshot_recovery.qnt:383`), and VERIFICATION lists the corresponding property ids as stated-normative (`docs/VERIFICATION.md:414`, `docs/VERIFICATION.md:415`, `docs/VERIFICATION.md:416`). This is not a faulty assumption as long as docs do not claim checked product semantics.
- **Adapter snapshot tiers: holds.** The prose-lane gap was real at the time, but it has since been ratified by a design feature. The three-tier model optimizes honest degradation: partial/no snapshot cannot fabricate live state, and durable command state remains authoritative from the core log (`docs/PROTOCOL.md:561`, `docs/PROTOCOL.md:562`; `.work/active/features/feature-session-identity-adapter-contract.md:179`, `.work/active/features/feature-session-identity-adapter-contract.md:283`).
- **Event/snapshot atomicity: holds with caveat.** The protocol correctly fails closed if the backend cannot provide atomicity (`docs/PROTOCOL.md:431`), but the formal snapshot atomicity properties remain in the draft snapshot/recovery model rather than promoted checks. This matches the current SPEC verification floor, which names snapshots/authority as stated-normative draft obligations and reserves checked-normative status for promoted-vector-backed properties (`docs/SPEC.md:32`; `docs/VERIFICATION.md:35`).

- **`feature-verification-contract-authority`: verified, with prior issue already caught and fixed.** This dependent explicitly re-opened authority between prose/models/contracts/vectors and selected a property-graded baseline (`.work/active/features/feature-verification-contract-authority.md:67`, `.work/active/features/feature-verification-contract-authority.md:74`). - **`feature-observability-operator-admin`: verified, no inherited false snapshot-recovery posture yet.** It is still drafting and only states that observability must design health/status, delivery trace, logs/metrics/event inspection, and CLI/admin debugging (`.work/active/features/feature-observability-operator-admin.md:16`, `.work/active/features/feature-observability-operator-admin.md:25`, `.work/active/features/feature-observability-operator-admin.md:26`, `.work/active/features/feature-observability-operator-admin.md:33`). Its design should consume the caveats above when deciding event inspection and degraded diagnostics, but no propagation fault exists today.

## Verdict

**holds-with-caveats.** The highest-value check passes: the persistence backend abstraction is a real Ports & Adapters boundary, with local/embedded deployment treated as v0 topology rather than domain semantics. The skipped design gate would mainly have recorded alternatives and clarified verification status. No faulty assumption requires reopening dependents: the crash/snapshot safety claims are coherent product obligations, but crash-specific and snapshot-recovery properties remain stated/draft formal obligations, not checked guarantees. Per operator constraint, no corrective items were filed.

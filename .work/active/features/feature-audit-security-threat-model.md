# Feature: Retroactive design-gate audit — v0 security, principal, and threat model

## Brief

`feature-security-threat-model` slipped through to `done` tagged `[prose]`, structurally skipping the design gate. Its scope defines the v0 threat model, the principal model (operator/device/browser-session/endpoint/adapter/actor), enrollment and revocation posture, grant shape and authorization algorithm, replay protection and command-issuer binding, emergency revocation and audit, and forbidden v0 deployments (e.g. internet-exposed unauthenticated core). These are security-architecture choices with high reversal cost and high propagation risk — exactly the class where a skipped alternatives evaluation is most dangerous.

3 downstream dependents (`feature-verification-contract-authority`, `feature-design-grant-shape`, `feature-lease-scope-decision`).

## Scope

1. **Alternatives evaluation** for each load-bearing security decision:
   - V0 threat model and explicit out-of-scope adversaries (which adversaries were considered and rejected vs omitted).
   - Principal model: operator/device/browser-session/endpoint/adapter/actor (vs flatter / vs richer-from-start).
   - Device/control-surface enrollment and revocation posture (the choices made — alternatives for enrollment ceremony, revocation speed, revocation propagation).
   - Grant shape and authorization algorithm (cross-ref `feature-design-grant-shape` which re-opened this — verify the audit doesn't duplicate; cover what that feature did *not*).
   - Replay protection and command-issuer binding (the compound-issuer model: operator + transport endpoint — alternatives?).
   - Emergency revocation and audit events.
   - Forbidden v0 deployments (internet-exposed unauthenticated core) — was this a conscious rejection with rationale?
   - The review-fix items (login throttling, authenticator setup, `Secure` cookie, adapter-core trust boundary, HTTPS clarification, delegation parent-grant seam) — each was a design decision made in-review; each likely has no alternatives record.
2. **Faulty-assumption hunt.** Re-derive each from current first principles. Flag any accident-of-prose. Pay special attention to: the adapter-core trust boundary (Patchbay controls remote/headless agents and potentially shell/job adapters — was the trust posture against a malicious/correct adapter actually pinned, or assumed?); whether the compound-issuer binding has an edge case the prose lane left open; whether the single-operator assumption baked in a security posture multi-human would have to reverse (not just defer).
3. **Propagation check** across the 3 dependents. Did `feature-verification-contract-authority` assume a security-posture property the skipped gate would have surfaced? Did `feature-design-grant-shape` already resolve the grant-shape open question, or is there residual debt? Did `feature-lease-scope-decision` (just done) inherit a security assumption about lessor authority?
4. **Verdict.** `holds` / `holds-with-caveats` / `faulty-assumption-found`.

## Alternatives evaluation

- **V0 threat model and out-of-scope adversaries.** Landed: defend the Patchbay boundary against unauthenticated access, unauthorized endpoint enrollment, CSRF, replay, revoked endpoints, wrong generation, stale adapter events, confused-deputy routing, capability-display mistakes, secret logging, bad deployments, and adapter-to-core bypasses (`docs/SECURITY.md:46-57`). Explicitly out of scope: compromised operator host/browser, malicious code already on a controlled host, malicious/backdoored harnesses beyond adapter-declared behavior, crypto library correctness, multi-operator workflows, HA/split-brain, and public multi-tenant hardening (`docs/SECURITY.md:63-69`). Alternatives: (a) broader hostile-host/hostile-harness threat model, optimizing defense depth but blocking v0 on unsolved OS/harness problems; (b) narrower web-only threat model, optimizing speed but leaving remote-control authority under-modeled; (c) landed boundary threat model, optimizing v0 safety where Patchbay can enforce. Why landed: matches research's v0 recommendation for server sessions, explicit authorization, CSRF, revocation, and audit (`.research/analysis/briefs/web-control-security.md:17-22`) while keeping external host/harness compromise as deployment/adapter discipline.
- **Principal model: operator/device/operator-session/endpoint/adapter/actor/runtime session/grant/authority domain.** Landed: keep all principal concepts explicit in one operator domain (`docs/SECURITY.md:25-38`; `docs/GLOSSARY.md:14-17`). Alternatives: (a) flat user+session model, optimizing simplicity but losing endpoint/device revocation and adapter identity; (b) richer multi-operator/RBAC model from v0, optimizing future governance but overbuilding; (c) landed explicit-but-single-operator model. Why landed: one human is product scope, not a reason to omit authority modeling (`docs/SECURITY.md:25`); research says the single-operator model should preserve future seams through actor/endpoint/session/grant records (`.research/analysis/briefs/web-control-security.md:28`).
- **Enrollment and authentication posture.** Landed: CLI/local-console first operator, one-time setup secret, password/passphrase primary authenticator, browser/CLI enrollment only after auth, adapter enrollment only through configured attachment material or adapter-specific trust root; labels are metadata (`docs/SECURITY.md:77-83`). Alternatives: (a) unauthenticated web setup wizard, optimizing ease but exposing first-run takeover; (b) mandatory passkeys/MFA/mTLS, optimizing hardening but blocking v0; (c) landed local bootstrap + password/passphrase with passkeys/MFA/mTLS reserved. Why landed: research supports local bootstrap and reserves MFA/passkeys while recommending stronger factors for remote exposure (`.research/analysis/briefs/web-control-security.md:28-35`).
- **Device/control-surface revocation.** Landed: current-session, all-session, endpoint/device, grant, and security-lockdown revocation; revocation prevents future authority and preserves history (`docs/SECURITY.md:193-210`). Alternatives: (a) session-only logout, optimizing simplicity but weak for lost endpoints; (b) grant-only revocation, optimizing protocol purity but weak for browser compromise; (c) landed layered revocation. Why landed: research calls emergency revocation a v0 necessity (`.research/analysis/briefs/web-control-security.md:21`, `.research/analysis/briefs/web-control-security.md:110-114`).
- **Grant shape and authorization algorithm.** Landed after re-open by `feature-design-grant-shape`: grant id, authority domain, subject actor, optional endpoint/class, target scope, allowed OperationKinds, provenance/time, optional expiration, revocation metadata and policy (`docs/SECURITY.md:145-160`; `docs/PROTOCOL.md:474-489`). Authorization is deny-by-default after payload/kind, issuer, target/generation, idempotency, expiration, and live grant checks (`docs/SECURITY.md:126-135`). Alternatives were evaluated there: minimal grants, endpoint-scoped grants, capability-set grants, delegation-in-v0, and status quo (`.work/active/features/feature-design-grant-shape.md:37-41`). Why landed: canonical OperationKinds avoid mutable adapter-capability authority, endpoint scoping preserves revocation, and `parent_grant_id` was removed as a misleading vacuous v0 field (`.work/active/features/feature-design-grant-shape.md:65-81`). This audit does not re-decide the grant field list.
- **Replay protection and command-issuer binding.** Landed: command id/idempotency key + expiration + target identity/generation + live grant before acceptance; retries return the existing record (`docs/SECURITY.md:126-137`). Compound issuer requires independently verified operator actor and transport endpoint, not payload sender (`docs/SECURITY.md:141-143`; `docs/VERIFICATION.md:235`). Alternatives: (a) bearer payload sender only, optimizing loose integration but confused-deputy vulnerable; (b) web-server-as-sole issuer, simpler but loses operator identity and future multi-operator audit; (c) landed compound issuer. Why landed: `feature-design-grant-shape` rejected web-server-as-sole principal because it would self-assert operator identity (`.work/active/features/feature-design-grant-shape.md:68`, `.work/active/features/feature-design-grant-shape.md:78`).
- **Emergency lockdown and audit.** Landed: lockdown is durable, survives restart, and exits only by the configured bootstrap trust channel; audit records are distinct from state-transition events and record security decisions without secrets (`docs/SECURITY.md:208-216`, `docs/SECURITY.md:221-236`). Alternatives: (a) routine web re-authentication clears lockdown, convenient but ineffective if routine credentials are held by the attacker; (b) manual DB/operator intervention, safe but operationally brittle; (c) landed bootstrap-channel exit. Why landed: channel separation is explicitly load-bearing (`docs/SECURITY.md:208`).
- **Forbidden v0 deployments.** Landed: forbid internet-exposed unauthenticated core, non-localhost HTTP authenticated browser sessions, browser-to-adapter authority bypass, adapter-display-name authority, and disabled acceptance/authz/revocation audit (`docs/SECURITY.md:248-254`). Alternatives: (a) allow anything self-hosted, optimizing adoption but normalizing unsafe remote control; (b) forbid all non-localhost v0, optimizing safety but killing LAN/VPN/reverse-proxy deployments; (c) landed allowed local/LAN/VPN/reverse-proxy-with-HTTPS envelope (`docs/SECURITY.md:242-246`).
- **Review-fix: login throttling.** Landed: rate-limit interactive login, track failed attempts against account plus useful network metadata, audit success/failure, avoid easy DoS (`docs/SECURITY.md:85`). Alternatives: no throttling, IP-only throttling, or account+network throttling. Why landed: research cites OWASP throttling and account-associated failed-login counters (`.research/analysis/briefs/web-control-security.md:34`).
- **Review-fix: authenticator setup.** Landed: password/passphrase for v0, passkeys/MFA reserved (`docs/SECURITY.md:79`; `docs/SECURITY.md:272-275`). Alternatives: no auth for local, mandatory WebAuthn/MFA, or landed password/passphrase with stronger-factor seam. Why landed: research says MFA is desirable but not mandatory for all audiences (`.research/analysis/briefs/web-control-security.md:35`).
- **Review-fix: `Secure` cookie and HTTPS clarification.** Landed: `__Host-` cookie with `HttpOnly`, `Secure` outside localhost, `SameSite=Strict`, `Path=/`, no `Domain`, and HTTPS/reverse-proxy requirement before non-localhost browser sessions (`docs/SECURITY.md:93-108`). Alternatives: JS-readable tokens/localStorage, HTTP for LAN, or landed server-side hardened cookie. Why landed: research favors server-side sessions and `Secure`/HTTPS outside localhost (`.research/analysis/briefs/web-control-security.md:17`, `.research/analysis/briefs/web-control-security.md:62`).
- **Review-fix: adapter-core trust boundary.** Landed: adapter endpoints enroll by configured attachment material/trust root and cannot self-assert core authority (`docs/SECURITY.md:82`); adapter-to-core bypass is in scope (`docs/SECURITY.md:57`); adapter identity is a principal with explicit registration lifecycle (`docs/PROTOCOL.md:547`); capability declarations are advisory UX, not authority/delivery gates (`docs/PROTOCOL.md:543`). Alternatives: (a) trust adapter display names/payloads, simple but spoofable; (b) require one global mTLS mechanism, strong but over-prescriptive; (c) landed adapter-specific trust roots with core-side identity/grant checks and mechanism left adapter-specific.
- **Review-fix: delegation parent-grant seam.** Landed after re-open: no live `parent_grant_id`/delegated-by field in v0; delegation is prose-reserved and future delegation must satisfy a precondition (`docs/SECURITY.md:160`; `docs/VERIFICATION.md:242-244`). Alternatives: keep reserved field, implement delegation now, or remove field. Why landed: `feature-design-grant-shape` found the field looked committed without semantics and moved the property out of v0 authority-safety obligations (`.work/active/features/feature-design-grant-shape.md:65`, `.work/active/features/feature-design-grant-shape.md:76`).

## Faulty-assumption hunt

- **Research chain survives.** The security research was adversarially verified as approved, with no remaining blockers; its Patchbay-specific controls were explicitly framed as design controls rather than laundered external requirements (`.research/analysis/briefs/web-control-security-verification.md:8`, `.research/analysis/briefs/web-control-security-verification.md:63`, `.research/analysis/briefs/web-control-security-verification.md:106-108`). No faulty grounding found.
- **Adapter-core trust posture: correct/trusted adapter endpoint is assumed; malicious enrolled adapter is not a v0 guarantee.** This is the high-risk check. The posture is pinned, not silently assumed: Patchbay protects the core boundary from unauthenticated/bypass/self-asserted adapter channels (`docs/SECURITY.md:57`, `docs/SECURITY.md:82`, `docs/PROTOCOL.md:635`), treats capabilities as non-authority (`docs/PROTOCOL.md:543`; `docs/VERIFICATION.md:236`), and rejects malformed/nonconformant authoritative snapshots instead of promoting them (`docs/PROTOCOL.md:564`). But v0 does **not** claim to defeat malicious code inside controlled hosts, compromised operator devices, malicious/backdoored harnesses beyond declared behavior, or adapter-specific behavior beyond declared adapter contracts (`docs/SECURITY.md:63-65`; `docs/VERIFICATION.md:292-294`). Classification: **trusted/correct adapter after enrollment is an assumption; malicious/compromised adapter behavior is out of v0 proof scope, with boundary checks/audit as containment.** That is a caveat, not a faulty assumption, because it is explicit enough in current docs and model scope.
- **Compound issuer survives, with a seam caveat.** The landed rule requires the core to verify both transport principal and operator-session evidence and not trust self-asserted operator identity (`docs/SECURITY.md:141-143`; `docs/VERIFICATION.md:235`). `authority.qnt` reserves/drafts `CompoundIssuer` and states accepted commands use verified session-derived actor identity, not self-asserted payload actor (`specs/seed/authority.qnt:334-345`). Caveat: exact web↔core evidence shape is deferred, and `feature-design-grant-shape` states the grant model needs revision if that seam cannot carry the evidence (`.work/active/features/feature-design-grant-shape.md:208`). No fault today because the requirement is pinned and the dependency is visible.
- **Single-operator posture does not bake a reversal.** V0 is one operator/authority domain, but data structures should not assume only one operator forever (`docs/SECURITY.md:25`, `docs/SECURITY.md:38`); protocol keys carry `authority_domain_id` as a federation seam (`docs/PROTOCOL.md:407-409`); multi-operator/shared authority is reserved (`docs/SECURITY.md:272`). Multi-human promotion would add workflows/policy, not reverse current deny-by-default/actor/grant/audit semantics.
- **Grant shape survives by later re-open.** The prose feature's riskiest grant decisions were re-opened and resolved in `feature-design-grant-shape`; the current docs match that outcome (`docs/SECURITY.md:145-160`; `docs/PROTOCOL.md:474-489`; `docs/VERIFICATION.md:230-238`). No residual grant-field debt found in this audit.
- **Replay and idempotency are correctly scoped.** The docs claim boundary dedup, not end-to-end adapter execution determinism (`docs/PROTOCOL.md:374-382`; `docs/VERIFICATION.md:186-188`). This is consistent with adapter-trust caveat and does not overclaim.
- **Browser/CSRF posture survives and is better checked than authority.** `csrf_browser.qnt` models server-side acceptance based on authenticated active session plus valid proof (`specs/seed/csrf_browser.qnt:59-60`) and carries promoted properties for unauthenticated rejection, missing-proof rejection, and revoked-session rejection (`specs/seed/csrf_browser.qnt:143-187`). It also models browser-local state as non-authority (`specs/seed/csrf_browser.qnt:203-207`). No fault found.
- **Emergency revocation/audit survives.** Lockdown durability and bootstrap-channel exit address the obvious re-auth bypass edge (`docs/SECURITY.md:208`); audit redaction and distinct audit records cover rejected attempts without leaking secrets (`docs/SECURITY.md:216`, `docs/SECURITY.md:234-236`). No fault found.
- **Review-fix decisions survive.** Login throttling, authenticator seam, secure cookies/HTTPS, adapter trust-boundary wording, and delegation removal each have current-doc support and no contradictory model claim (`docs/SECURITY.md:85`, `docs/SECURITY.md:95-97`, `docs/SECURITY.md:160`; `docs/VERIFICATION.md:242-244`).

No re-open required.

## Verdict

**holds-with-caveats.** No faulty assumption found requiring corrective-item filing. The core security posture holds under the stated v0 boundary: Patchbay verifies enrolled endpoints/control surfaces, enforces grant checks before acceptance, denies by default, rejects self-asserted identities, treats adapter capabilities as non-authority, scopes idempotency to the Patchbay boundary, and reserves multi-operator/delegation/leasing seams. The caveats are security-important and should stay visible: (1) a malicious/compromised enrolled adapter or host is not defeated by v0 semantics beyond boundary checks, conformance rejection, and audit; (2) `CompoundIssuer` and authority safety are still stated-normative/draft, with exact web↔core evidence shape deferred.
